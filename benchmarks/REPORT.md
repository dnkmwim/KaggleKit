# Kaggle 数据获取与筛选方法测评报告

> 测量环境：未认证调用 Kaggle 公开元数据接口，REST 受控 4 并发，样本为 `classification` 标签下实时取得的同一组 40 个数据集。
> 测速结果受网络、限流和本机环境影响，不应把单次结果当作普遍结论；复现方式见下方“数据获取速度实测”。

## 结论

在本轮 REST 获取实验中，4 并发相较串行显著缩短总耗时，因此当前推荐 REST API 加受控并发。在当前已完成人工有效标注的样本中，关键词检索精度最高；语义检索能补充同义词、跨语言和自然语言召回，但也更容易误召回。混合检索目前没有证明整体质量高于关键词，适合继续作为补召回和排序方案。

## 一 本工具的数据获取流程

| 步骤 | 具体内容 |
|---|---|
| 输入目标 | 输入关键词，或者直接给出数据集的 owner/slug。 |
| 发现候选 | 调用 Kaggle 数据集列表接口，找到可能符合要求的数据集。 |
| 补全详情 | 逐个读取数据集详情和文件清单，补齐描述、作者、标签、许可证、更新时间和文件信息。 |
| 整理结果 | 合并同一数据集的信息，并检查公开性和字段完整度。 |
| 输出文件 | 每个数据集生成一份 Markdown，同时生成 JSON 汇总，供检索和 Agent 使用。 |

它的作用：本工具是一套“读取 Kaggle 数据集资料并整理成统一文本”的样例。它抓取的是元数据，不是批量下载 CSV、图片或 ZIP 原始文件。

## 二 几种数据获取方式对比

| 方式 | 具体内容 | 优缺点 | 本次结论 |
|---|---|---|---|
| REST API | 程序直接请求 Kaggle 官方接口。 | 字段完整；并发、重试和超时都能控制。 | 正式方案优先 |
| Kaggle CLI | 每查一个数据集，执行一次官方命令。 | 容易使用；反复启动命令有开销，本次字段不足。 | 适合临时查询 |
| kagglehub | Python 下载工具，重点是下载和缓存文件。 | 适合取原始文件，不适合批量发现元数据。 | 不参加元数据排名 |
| 网页抓取 | 模拟浏览器读取网页并提取信息。 | 页面变化后容易失效，维护成本高。 | 只作接口缺字段时的备用 |

## 三 如何过滤并找到指定数据

| 方法 | 大白话解释 | 强项 | 适合位置 |
|---|---|---|---|
| 规则过滤 | 先按公开性、资源类型、标签和必要字段排除不合格数据。 | 快、结果容易解释。 | 检索前第一道筛选 |
| 关键词匹配 | 查询词要和标题、标签或描述中的词直接对应。 | 精确、速度快。 | 主检索 |
| 词袋和 TF-IDF | 把文字拆成词；越少见又重复出现的词权重越高，再比较两段文字是否相像。 | 便宜、能排序。 | 轻量级词面排序 |
| 语义相似度 | 把文字变成一串数字，比较两段文字表达的意思是否接近。 | 能处理同义词和自然语言。 | 补充召回 |
| 混合检索 | 分别跑关键词和语义检索，再合并两份排名。 | 兼顾精确命中和额外召回。 | 最终候选排序 |

本轮选择：本轮新增实测 TF-IDF，因为它是原报告中已经列出、但尚未闭环测试的方法。没有继续堆叠 BM25、模糊匹配和重排模型：BM25 与 TF-IDF 同属词面排序，当前人工标签覆盖也不足以支持更多方法的公平质量排名。

## 四 数据获取速度实测

测试对象：Kaggle 公开 classification 标签下实时取得的同一组 40 个数据集。两种方式使用相同数据和字段口径。

| 方式 | 运行方式 | 总耗时 | 吞吐量 | 成功数 | 字段完整度 |
|---|---|---|---|---|---|
| REST 串行 | 一个接一个抓 | 83.819 秒 | 0.477 条/秒 | 40/40 | 99.62% |
| REST 4 并发 | 同时抓 4 个 | 21.439 秒 | 1.866 条/秒 | 40/40 | 99.62% |

实测结论：REST 4 并发比 REST 串行少用 74.4% 的时间，吞吐提升到 3.91 倍，成功率和字段完整度相同。这个实验只证明 REST 内部并发优于串行；没有证明它比所有其他获取方式都快。

复现：

```bash
kagglekit acquisition-benchmark \
  --source tag:classification \
  --sample-size 40 \
  --workers 4 \
  --output benchmarks/results/report.json
```

## 五 检索速度对比

| 方法 | 平均 | 中位数 | P95 | 冷启动或建索引 | 说明 |
|---|---|---|---|---|---|
| 关键词 | 10.716 ms | 10.098 ms | 18.000 ms | 无模型冷启动 | 24 条原查询 |
| TF-IDF | 0.288 ms | 0.312 ms | 0.422 ms | 431 条建索引 3.051 ms | 24 条查询，Top-5 |
| 语义 | 热启动 9.986 ms | 9.552 ms | 12.677 ms | 首次约 2254 ms | 首次加载模型较慢 |
| 混合 | 总计 114.761 ms¹ | 19.722 ms | 29.881 ms | 包含语义模型 | 热启动通常约 14–30 ms |

¹ 混合平均值包含第一次语义模型加载，因此被冷启动拉高；中位数和 P95 更接近日常热启动速度。TF-IDF 时间只计算本地检索，不包含从 Kaggle 获取候选数据的网络时间。

## 六 检索质量对比

统计范围：原实验包含 24 条查询和 335 条返回结果。去重后有 196 个 query-dataset 组合，其中 135 个有有效人工标签；61 个因链接无法唯一定位而不进入质量统计。下表前三种方法都以各自已获得有效人工判断的结果为分母。

| 方法 | 返回数 | 有效人工判断 | 直接相关 | 相关或部分相关 | 不相关 | 零结果查询 |
|---|---|---|---|---|---|---|
| 关键词 | 95 | 73（76.8%） | 80.8% | 97.3% | 2.7% | 4/24 |
| 语义 | 120 | 91（75.8%） | 61.5% | 79.1% | 20.9% | 0/24 |
| 混合 | 120 | 93（77.5%） | 71.0% | 81.7% | 18.3% | 0/24 |
| TF-IDF | 107 | 107（100%） | 52.3% | 71.0% | 29.0% | 2/24 |

TF-IDF 的 107 条返回结果已经全部完成人工标注。关键词、语义和混合仍有部分结果没有有效人工标签，所以比较时必须同时看“有效人工判断覆盖率”。此外，TF-IDF 候选库为 222 条，原三种方法候选库为 430 条，本轮结论适合做工程选型，不作为严格同库算法论文结论。

## 七 按查询类型拆分表现

| 查询类型 | 关键词 | 语义 | 混合 | TF-IDF | 怎么理解 |
|---|---|---|---|---|---|
| 精确关键词 | 100%｜20 | 100%｜20 | 100%｜20 | 95.0%｜20 | 四种方法都稳定。 |
| 同义词表达 | 68.8%｜19 | 62.5%｜20 | 80.0%｜20 | 35.0%｜20 | 混合最好；TF-IDF 容易只抓通用词。 |
| 中文查询 | 84.6%｜14 | 43.8%｜20 | 55.6%｜20 | 36.8%｜19 | TF-IDF 和语义都容易漏掉复合限定。 |
| 自然语言任务 | 100%｜12 | 92.3%｜20 | 92.3%｜20 | 50.0%｜18 | 关键词更准但返回少；语义与混合补召回。 |
| 宽泛查询 | 86.7%｜20 | 93.3%｜20 | 100%｜20 | 70.0%｜20 | 宽泛查询区分能力有限。 |
| 低信息和 OOD | 16.7%｜10 | 0%｜20 | 6.3%｜20 | 0%｜10 | TF-IDF 对两个无意义查询返回空；语义与混合强行返回。 |

表中百分比为各类型已获得有效人工判断结果的直接相关率，条数为实际返回数。各组只有 4 条查询，只做描述性比较。TF-IDF 在精确词上表现好，但在同义词、中文复合查询和自然语言任务上明显下降；它的优势是两个无意义查询都自然返回空结果。

## 八 方法综合对比

| 方法 | 速度和成本 | 擅长 | 主要弱点 | 无意义查询 | 在方案中的位置 |
|---|---|---|---|---|---|
| 规则过滤 | 最快；几乎无额外成本 | 公开性、类型、标签、必要字段等硬条件 | 不能判断复杂相关性 | 能直接拒绝部分非法输入 | 检索前 |
| 关键词 | 约 10.7 ms；无需模型 | 英文精确词；结果容易解释 | 同义词、跨语言可能漏召回 | 可以自然返回空结果 | 高精度主通道 |
| TF-IDF | 约 0.29 ms；索引很轻 | 词面相似度排序；部署便宜 | 不理解句意；依赖分词和词典扩展 | 完全无词重叠时可返回空 | 轻量备选或候选排序 |
| 语义 | 热启动约 10 ms；有模型和向量索引成本 | 同义词、跨语言、自然语言 | 会把只沾边的结果排上来 | 容易强行返回近邻 | 补召回 |
| 混合 | 热启动约 14–30 ms；维护两路索引 | 兼顾关键词与语义候选 | 当前整体质量未超过关键词 | 仍需阈值才能拒绝 | 最终候选合并 |
| 最低相关度 | 额外成本低；阈值需校准 | 阻止 OOD 查询强行返回 | 阈值过高会漏掉真实结果 | 最有针对性 | 所有检索后的保护层 |

## 九 建议采用的方案

| 环节 | 推荐做法 | 依据 |
|---|---|---|
| 数据获取 | Kaggle REST API 加 4 并发、超时重试和 429/服务器错误退避 | 40 条实测中比 REST 串行快 3.91 倍，字段完整度相同 |
| 第一步筛选 | 检查公开性、资源类型、精确标签、必要字段和排除词 | 先删除确定不合格的候选，便宜且可解释 |
| 主要检索 | 关键词检索加受控同义词和中英扩展 | 当前有效人工样本上精度最高 |
| 补充召回 | 语义检索 | 能找到标题不直接包含查询词、但内容相关的数据 |
| 最终排序 | RRF 合并两路结果；再设置最低相关度，允许返回空结果 | 兼顾候选覆盖，并减少无意义查询误召回 |

最终判断：当前最合适的组合是“规则过滤 → 关键词主检索 → 语义补召回 → 混合排序 → 最低相关度拒绝”。关键词在当前已标注样本上精度最高；语义检索负责补充同义词、跨语言和自然语言候选；混合检索目前没有证明整体质量优于关键词，但能把两类候选放进同一排序。

## 十 局限与后续工作

| 局限项 | 为什么还不能下结论 | 下一步 |
|---|---|---|
| 严格同库复测 | TF-IDF 使用 222 条候选，另外三种方法使用原 430 条候选。 | 如需要研究级结论，再冻结同一候选快照统一复跑。 |
| Precision@K 和 nDCG@K | 原三种方法仍有部分返回结果未完成人工判断。 | 补齐剩余标签后计算，不能把未判断项当成不相关。 |
| 最低相关度阈值 | 已确认语义和混合存在 OOD 误召回，但尚未形成阈值曲线。 | 同时使用正常查询和 OOD 查询校准误拒绝与误召回。 |
